# 안건

여러 사람이 각자 AI 를 돌리며 한 저장소에서 협업할 때, 작업이 겹치고 머지 순서가 꼬이는 문제와 하네스 규칙이 적절한지 점검

## 상황 설명
* 2026-11-05, 같은 시기에 PR 3개가 열림
    * #9(성호님): 하네스 규칙과 센서를 travel-crumbs 에 맞춤. 매니페스트 허용 목록에 NAVI_ROUTE · NAVI_ROUTE_SEARCH 를 추가하고 DO 를 허용함
    * #10(희주님): CI 에 app 잡 추가. 앱 빌드 · 린트 · 테스트 · 매니페스트 검사
    * #13(희주님): 앱 뼈대(#6) 구현
* 세 PR 이 서로 얽힘
    * #10 · #13 의 app 잡이 빨강. 원인은 #9 가 고치는 매니페스트 규칙
    * #9 와 #10 이 같은 파일(team-workflow/SKILL.md)을 고침
    * ADR 번호 0013 을 두 PR 이 동시에 씀
* 해결 순서: #9 → #10(ADR 0015 로 변경 · rebase) → app-shell/main sync → #13
* 문제는 머지 전에 발견됨. 성호님이 PR 코멘트로 알림

## 걱정되는 점
* 사람이 PR 설명이나 코멘트를 바로 이해하지 못하고 AI 에게 다시 물어봄. 문서가 「AI 가 쓰고 AI 가 읽는」 형태로 흘러감
* 각자의 AI 는 develop 만 보고 일함. 다른 사람이 지금 무엇을 하는지 모름
* 사고마다 규칙을 추가하면 하네스가 계속 무거워짐. ADR 번호 충돌도 「결정은 전부 ADR 로」라는 규칙이 만든 부산물
* 사람이 늘어날수록(AI 수도 같이 늘어날수록) 겹침은 더 잦아짐

## 하네스 규칙이 괜찮은지 판단 방법
* .claude/log
    * 누가 실제로 열어 보고 있는지
    * 문제를 추적할 때 실제로 도움이 됐는지.
* PR
    * AI 에게 설명을 다시 물어보지 않고 이해하는지
    * issue 생성부터 머지까지 걸리는 기간. 스펙 PR → 구현 PR → develop PR 단계가 각각 값을 하는지
* 실제로 쓰이는지
    * 문제를 잡은 것이 규칙 · 센서였는지, 사람의 대화였는지
    * 글로만 있는 규칙 중 지켜지지 않은 것. 센서로 바꾸거나 없앰
* 2주 뒤 위 항목을 다시 확인하는 회고 자리

## 원인 파악
* 사람끼리의 소통이 쉽지 않다
    * 같은 회사, 같은 프로젝트 팀이어서 바로 뒤에 앉아 있는 상황이라면
        * 성호님이 희주님께 「제가 app 관련 하네스를 고칠게요」라고 말하고 그 범위에서만 작업한 뒤 빠르게 병합했다면, 희주님은 그 뒤에 CI 를 붙여 처음부터 녹색으로 시작했을 것
    * 실제로는 각자 AI 와 따로 작업하다가 PR 에서야 서로의 작업을 알게 됨
* 「지금 누가 무엇을 하는지」 보이는 곳이 없음
* 하네스에 빠진 규칙
    * ADR 번호를 동시에 고를 때의 규칙이 없음
    * PR 간 의존(먼저 머지돼야 하는 PR)을 적는 칸이 없음
* 세팅이 미뤄진 것
    * 하네스는 「첫 이슈에서 app 잡을 만든다」고 정했지만 실제로는 빠져 있었음. 그래서 구현이 진행되는 와중에 CI 추가가 뒤늦게 끼어듦

## 해결 방향
* 사람끼리 먼저 맞춤. 작업 시작 전에 「나 지금 ○○ 건드려요」 한 줄(메신저나 짧은 스탠드업)
* 영역별 담당. 하네스(.claude/ · CI · CLAUDE.md)는 한 번에 한 사람만 손댐
* 사람용 요약을 맨 위에. PR 본문 첫 세 줄을 「무엇 · 왜 · 머지 전에 사람이 할 일」로 고정
* 규칙을 더하기보다 덜어내는 쪽부터 검토. 위 판단 방법으로 안 쓰이는 규칙을 찾아 줄임
